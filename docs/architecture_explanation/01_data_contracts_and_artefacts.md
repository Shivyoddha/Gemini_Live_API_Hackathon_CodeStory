# Data Contracts and Artefacts

This document specifies the key data structures and file artefacts produced and consumed across the CodeStory backend, pipeline, and frontend.

---

## 1. HTTP API Request/Response Shapes

### POST /run-pipeline

- **Request body:** `{ "url": string, "session_id"?: string }`
- **Response (200):** `{ "jobId": string }`
- **Response (400):** `{ "error": string }` (e.g. "url is required")

### GET /pipeline-status/:id

- **Query:** `session_id` (optional, default "dev")
- **Response (200):** `{ "status": string, "message": string }`  
  `status` is one of: `queued`, `cloning`, `running`, `indexing`, `done`, `error`
- **Response (404):** `{ "error": "Job not found" }`

### GET /content

- **Query:** `session_id` (optional, default "dev")
- **Response (200):**
  ```json
  {
    "docs": [
      { "filename": string, "module": string, "text": string }
    ],
    "slides": [
      { "module": string, "filename": string, "text": string }
    ],
    "project_name": string
  }
  ```
- **Response (500):** `{ "error": string }`

### GET /search-docs

- **Query:** `q` (required), `session_id` (optional)
- **Response (200):** `{ "chunks": [ { "text": string, "source": string } ] }`
- **Response (400):** `{ "error": "q parameter is required" }`

---

## 2. WebSocket First Message (Client → Server)

- **JSON:** `{ "bearer_token"?: string, "service_url": string }`
- `service_url`: Vertex AI BidiGenerateContent WebSocket URL (e.g. `wss://.../ws/google.cloud.aiplatform.v1beta1.LlmBidiService/BidiGenerateContent`).
- If `bearer_token` is omitted, the server uses Application Default Credentials to obtain a token.

---

## 3. Pipeline Output Layout (Session or Workspace)

Under the pipeline `--output-dir` (e.g. `/tmp/sessions/<session_id>/` or workspace root):

```
<output-dir>/
├── documentation/
│   ├── *.md                    # One file per blueprint section
│   └── documentation_manifest.json   # Optional: section_id per filename
├── slides/
│   └── <module_name>/          # e.g. 01_project_overview
│       ├── 001_<slide_title>.md
│       ├── 002_<slide_title>.md
│       └── speaker_script.md
├── documentation_sections.zip  # ZIP of documentation/
├── repository_presentation.zip # ZIP of slides/
└── slide_index.json            # Machine-readable index for Live API narrator
```

---

## 4. slide_index.json Schema

Generated by `slide_workflow.build_slide_index()`. Consumed by the Multimodal Live API narrator to know slide order, file paths, and speaker script word counts.

```json
{
  "sections": [
    {
      "section": "Section Title",
      "slides": [
        {
          "slide_number": 1,
          "title": "Slide Title",
          "file": "<module_name>/001_slide_title.md"
        }
      ],
      "speaker_script_file": "<module_name>/speaker_script.md",
      "script_word_count": 42
    }
  ]
}
```

- **section:** Human-readable section title (matches `## Section` in agent output).
- **slides:** Ordered list; `file` is path relative to the slides root (same as inside the presentation ZIP).
- **speaker_script_file:** Path to the section’s speaker script, or `null` if none.
- **script_word_count:** Word count of that script (for pacing).

---

## 5. documentation_manifest.json (Optional)

Produced by the documentation agent. Used by the server when loading content to map doc filenames to section IDs (e.g. for consistent `module` keys).

- **Structure:** `{ "sections": [ { "filename": string, "section_id": string } ] }`

---

## 6. Doc and Slide Module Keys

- **Docs:** `module` is derived from the doc filename: stem lowercased, `_and_` replaced with `__` (e.g. `01_Project_Overview.md` → `01_project_overview`). If a manifest exists, `section_id` can override.
- **Slides:** `module` is the directory name under `slides/` (e.g. `01_project_overview`). Matching ensures the dashboard can show “Doc” for a module and align it with the same module’s slides.

---

## 7. ChromaDB Indexing (Implementation Note)

- **Indexing:** The server is designed to index content after the pipeline completes via `index_content_into_chroma(session_id)`. The only implementation present is `_index_content_into_session_chroma(session_id, content)`, which expects a `content` dict with `docs` and `slides` (same shape as `/content` response).
- **Correct behaviour:** A wrapper should load content with `load_content(session_id)` and call `_index_content_into_session_chroma(session_id, content)`. Without this wrapper, post-pipeline indexing may not populate the session collection, so `/search-docs` could return no results until content is loaded and indexed by some other path.
- **Chunking:** Doc text is split into word-based chunks (default 500 words); each slide is one chunk. Metadata includes `source`, `type` ("doc" or "slide"), and for slides `module`.

---

## 8. GCS Object Layout (Production)

When `GCS_BUCKET` is set and the pipeline completes, the backend uploads session output to:

- `gs://<bucket>/<session_id>/documentation/<filename>.md`
- `gs://<bucket>/<session_id>/documentation/documentation_manifest.json` (if present)
- `gs://<bucket>/<session_id>/slides/<module>/<filename>.md`
- `gs://<bucket>/<session_id>/slides/<module>/speaker_script.md`

Only `.md` and `documentation_manifest.json` are uploaded. The `/content` handler reads from these paths when `session_id` is provided and GCS is configured.
